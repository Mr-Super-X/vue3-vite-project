## 2. 问题清单（按严重度分级）

### 2.1 HIGH —— 功能缺陷 / API 失实

#### H1 `element` expose 恒为 null，连带 `clearSelection` 无法清 UI 勾选

- **证据**：`useTable.ts:104` 创建 `tableRef`；`ProTable.vue:210` 以 `element: table.tableRef` 暴露；但全库无任何位置给 `table.tableRef` 赋值（模板里 `ref="proTableEl"` 是另一个独立 ref，`ProTable.vue:122`）。
- **影响**：`types/index.ts:306-313` 承诺"el-table 表格实例……回退完成后恒有值"——**恒为 null，文档失实**。连带 `clearSelection()`（`useTable.ts:176-178`）只清内部 `selectedRows` ref，拿不到 el-table 实例就无法调用其 `clearSelection()`，**UI 勾选状态与 API 状态脱节**（多选场景父组件调 `clearSelection()` 后表格勾选框仍然勾着）。
- **方案**：`ElementTableBody` 内 ElTable 挂模板 ref 并 `defineExpose` 转发；`ProTable.vue` 把 `proTableEl` 的底层实例同步写入 `table.tableRef`；`clearSelection` 增加 `tableRef.value?.clearSelection?.()` 调用（可选链兜底 vxe 引擎）。
- **风险**：低。纯补接线，不改既有行为路径；vxe 引擎下 `element` 维持 null（与类型注释一致）。

#### H2 列设置持久化只恢复列顺序，可见性/固定列刷新后丢失

- **证据**：`persist()` 写入 `{ order, visible, fixed }`（`useColumns.ts:126-138`），但加载路径只读 `persisted?.order`（`useColumns.ts:97`）。`visibleKeys` 初始化恒为全列（`useColumns.ts:83`），`persisted.visible` / `persisted.fixed` **无任何读取点**。
- **影响**：`tableKey` 承诺的"列设置持久化"（`types/index.ts:260-261`、ARCHITECTURE.md 状态归属表）只兑现了 1/3——用户隐藏的列、固定的列刷新页面后全部复原。
- **方案**：`useColumns` setup 时回填——`visibleKeys` 初始取 `persisted.visible` 中值为 true 的键；`fixed` 经 `toggleFixed` 同路径写入 allColumns 副本。补 spec：mock `Local.get` 返回完整 setting，断言三字段均恢复。
- **风险**：中低。改变既有（有缺陷的）行为；用户已"习惯"刷新重置可见性，恢复持久化是向文档承诺对齐，属修复而非破坏。

#### H3 僵尸配置字段：类型层承诺、运行时零读取（6 处）

| 字段 | 声明位置 | 运行时读取点 |
|------|----------|--------------|
| `RowEditConfig.trigger` / `exclusive` | `types/index.ts:34-35` | 无（触发硬编码 dblclick，`ProTable.vue:266`；exclusive 无实现） |
| `TreeConfig.showLine` | `types/index.ts:50` | 无（`useTableCapabilities.ts:111` 透传后 `useTreeData` 从不读） |
| `CellSpanConfig.judge` / `spanHeader` | `types/index.ts:58-64` | 无（仅列级 `col.span.judge` 生效，`useCellSpan.ts:38`）；`direction` 仅用于 warn（`useTableCapabilities.ts:190`） |
| `ProColumn.isFilterEnum` | `types/index.ts:178` | 无（全库 grep 零命中） |
| `ProColumn.fieldNames` | `types/index.ts:180` | 无（SearchForm 直接读 `col.enum`，`SearchForm.vue:115`） |
| `filter-change` 事件透传（spec D3 承诺） | `2026-09-08-protable-next-iteration-design.md` D3 | 无 emit 实现 |

- **影响**：API 虚标——业务方按类型提示配置了字段，运行时静默无效，属"静默吞配置"，比报错更伤信任。
- **方案（二选一，建议 A）**：
  - **A. 移除**：分支未合 master，直接删除字段 + CHANGELOG 记录。`isFilterEnum`/`fieldNames`/`showLine`/`spanHeader`/全局 `judge`/`trigger`/`exclusive` 均无真实使用方。
  - **B. 实现**：仅对有真实需求的字段立项实现（当前无）。
- **风险**：A 方案为类型层破坏（运行时零影响）；若有未知业务方已写字段，TS 编译期即暴露，可控。

#### H4 reset / setSearchParams 在 page≠1 时触发双请求

- **证据**：`ProTable.vue:77-80` fetchHook：`table.setPage(1)` 触发 `useTable.ts:212-214` 的 watch → 第一次 `refresh()`（fire-and-forget）；紧接着 `await table.refresh()` 第二次执行。`useTable.onSortChange`（`useTable.ts:193-200`）处理同场景时已用"page≠1 只 setPage 由 watch 触发，否则手动 refresh"的正确模式——**两处策略不一致**。
- **影响**：每次重置/程序化搜索在跨页时多发一次请求（靠 useRequest AbortController 取消前者兜底，但请求已发出，服务端有感）。
- **方案**：fetchHook 对齐 onSortChange 模式——`page !== 1 ? setPage(1) : await refresh()`。
- **风险**：低。需补 useTable 或集成测试：page=3 时调 reset，断言 requestApi 只调用 1 次。

### 2.2 MEDIUM —— 架构/可维护性

#### M1 `engine` 死参数（3 个 composable）

- **证据**：`useSearch.ts:37`、`useColumns.ts:20`、`useTable.ts:36` 的 options 均声明 `engine: Ref<TableEngine>`，但三个函数体从不读取（仅 `useTableCapabilities.ts:92` 真正消费）。调用方（`ProTable.vue:71,76,85`）与 7+ 处 spec 被迫传一个无意义参数。
- **影响**：泄漏的抽象——引擎关注点涂抹到不需要它的层；读者会误以为这些 composable 有引擎分支逻辑。
- **方案**：删除三处 options 字段 + 同步 ProTable.vue 调用与 spec。

#### M2 SearchForm Proxy 双写反模式

- **证据**：`SearchForm.vue:49-55`——Proxy `set` 直接写 `props.searchParams`（父层 `search.searchParams.value` 同一对象引用），**又** emit `update:searchParams`，父层 `updateParams` 再 `Object.assign` 同一对象（`useSearch.ts:98-100`）。注释"避免直接修改 prop 触发 lint"表明作者知情绕行。
- **影响**：单向数据流名存实亡；一次输入产生"直接突变 + 事件回写"两条写入路径，后续加拦截（如输入防抖、脏检查）时双路径必然踩坑。
- **方案**：子组件改受控——不写 props 对象，仅 `emit('update:searchParams', { key, value })`，父层统一写 `searchParams`。

#### M3 `engine` expose 快照过期

- **证据**：`ProTable.vue:211` `engine: engineRef.value` 在 setup 时捕获；`handleEngineFallback`（`ProTable.vue:180-182`）修改 engineRef 后，expose 仍报告 `'vxe-table'`，与 `types/index.ts:314`"当前激活的引擎"矛盾。
- **方案**：改 `get engine()` 或暴露 `computed(() => engineRef.value)`（对 expose 对象用 getter）。

#### M4 ProTable.vue 350 行超项目红线

- **证据**：项目规则"业务组件 ≤300 行，上浮 ≤30"→ 330 行上限，当前 350。
- **方案**：把 §2.1-H1 修复时的 ref 桥接、M3 的 expose 组装、`handleXxx` 桥接函数群下沉为一个 `useProTableBridge`（或扩展现有 capabilities），目标 ≤300 行。

#### M5 props.columns 动态变更不响应（未文档化）

- **证据**：`useColumns.ts:82` 仅 setup 时 `cloneColumns(props.columns)` 快照；`searchColumns` 也是一次性 filter（`useColumns.ts:123`）；全库无 `watch(() => props.columns)`。
- **影响**：异步加载列配置（常见中后台场景：先拉列元数据再渲染）静默失效。
- **方案（二选一）**：A. watch + re-clone（需设计与用户已改列设置的合并策略）；B. 文档化"columns 须首渲染前就绪"。**建议 B（YAGNI），真实需求出现再做 A。**

#### M7 expose 类型与运行时不一致 + useRowEdit 伪私有命名

- **证据**：`ProTableExpose` 的 v2 方法全部 optional（`types/index.ts:319-329`），但 `v2Expose`（`useTableCapabilities.ts:205-249`）**恒提供全部 7 个方法**（内部做能力存在性守卫）。`useRowEdit` 的 `_start/_cancel/_save`（`useRowEdit.ts:43,47,52`）被 `ProTable.vue:266`、`useTableCapabilities.ts:206-223`、`ElementTableBody` 跨层调用——下划线"私有"约定与真实可见性矛盾。
- **方案**：v2 方法类型改 required（与运行时对齐）；`_start/_cancel/_save` 去下划线更名（内部 API，同步 spec）。

#### M8 SearchForm 折叠行为与文档矛盾（待澄清意图）

- **证据**：文件头注释"默认前 searchRows×2 行"（`SearchForm.vue:6`），但 `collapsed = ref(false)`（`:59`）默认展开全部；且 `searchRows × 2` 语义混乱（searchRows=3 → 6 个搜索项，4 列布局下是 1.5 行而非"3 行"）。
- **方案**：与 spec 对齐意图后统一——默认收起（`ref(true)`）或改注释；`searchRows` 语义重命名（如 `collapseAfterRows`）或改按行计算（`searchRows × 4`）。

## 3. 专项评估：API 分层与组件透传

| 维度 | 结论 | 依据 |

| 插槽透传 | ✅ 合理。双引擎 `v-for $slots` 全量转发契约一致；TableHeader 具名插槽显式桥接 | `ProTable.vue:238-243,271-273,290-292` |
